# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**PolicyPilot** — a RAG-based voice/text assistant for Health, Life, and Motor insurance policies. Users upload policy PDFs with no manual tagging; the backend auto-classifies the policy type and extracts a structured summary, then answers questions by retrieving from a Postgres/pgvector store and generating with Gemini. FastAPI backend (`backend/`, including its `core`/`chains`/`rag`/`voice`/`services` submodules) + React/Vite/Tailwind frontend (`frontend/`), with a sidebar-driven dashboard shell, a persistent multi-session Chat page, a floating quick-chat/voice assistant on every page, and voice I/O (Whisper STT, local Kokoro TTS) with silence-based auto-stop recording.

## Commands

This project uses `uv` for Python dependency management (see `pyproject.toml` / `uv.lock`) and `npm` for the frontend (see `frontend/package.json`).

```bash
# Install Python dependencies (--group ingest adds Docling + torch, needed to ingest PDFs;
# the web app alone runs without it)
uv sync --group ingest

# Apply database migrations (needed once on a fresh database, and after pulling new ones).
# Uses MIGRATION_DATABASE_URL (Neon's direct URL) if set, else DATABASE_URL
uv run alembic upgrade head

# New migration after editing backend/models.py (read the generated script before applying)
uv run alembic revision --autogenerate -m "what changed"

# Re-index every uploaded policy (safe with the backend running; --only 3,5 for specific ones)
uv run python -m backend.rag.ingest --reindex-all

# Retrieval/answer eval over evals/questions.jsonl (--answers also generates and checks answers)
uv run python -m evals.run_eval --answers

# Run the FastAPI backend (from repo root; the schema must already be migrated)
uv run uvicorn backend.main:app --reload

# Run the frontend dev server (separate terminal, from frontend/)
cd frontend && npm install && npm run dev
```

The frontend expects the backend at `http://localhost:8000` (override via `frontend/.env`'s `VITE_API_BASE_URL`) and the backend's CORS allows `http://localhost:5173` (`backend/config.py:VITE_DEV_ORIGIN`).

`.env` needs `GOOGLE_API_KEY` (Gemini chat/extraction), `JINA_API_KEY` (reranking; the backend refuses to start without it) and `DATABASE_URL` (Neon Postgres, `postgresql+psycopg://...`, pooled URL; `MIGRATION_DATABASE_URL` optionally holds the direct URL for Alembic). The vector store needs Postgres with pgvector, so `chunks`-backed retrieval doesn't work on the SQLite fallback. `ENV=prod` makes the backend refuse to start with the default `SECRET_KEY`.

There are no test, lint, or build scripts configured for the backend (`evals/run_eval.py` is the closest thing to a test — run it before and after any retrieval/chunking change); the frontend has `npm run build` (tsc + vite build), `npx oxlint src`, and `npx tsc -b`, but no test suite.

## Architecture

### Request flow

`backend/services/chat_service.py:answer_question(message, history, policy_id=None, db=None, voice=False)` is the shared entry point used by **both** chat surfaces (`backend/routers/chat.py`'s ephemeral `POST /chat` and `backend/routers/chat_sessions.py`'s persistent `POST /chat/sessions/{id}/messages`):

1. If `policy_id` is already known (a Chat page session pinned to a policy, or the floating assistant on a policy's detail page), it skips straight to retrieval+generation: `backend/chains/query_rewriter.py:rewrite_query(question, history)` always runs (no trigger-word gate) to fold chat history into a standalone search query — this is what makes follow-ups like "and the waiting period for that?" retrieve correctly — and the policy's `policy_type` is read directly off its `Policy` row (no LLM call needed).
2. Otherwise (unscoped chat), `backend/chains/policy_resolver.py:resolve_policy(question, history, policies)` makes one structured-output call that replaces the old separate clarification/policy-detection/rewrite steps: it rewrites the question into a standalone query, classifies `policy_type` (`health`/`life`/`motor`/`both`/`unknown`), and — grounded in the user's actual policy list (id/type/insurer/product name) plus chat history — either resolves a single `resolved_policy_id` unambiguously, or sets `needs_clarification` with a `clarification_question` and a list of candidate policies (only when the user genuinely has more than one policy of the relevant type and history doesn't narrow it down). A clarification response short-circuits before retrieval and carries `clarification_options: [{id, label}]` for the frontend to render as pickable chips; picking one persists that `policy_id` onto the session (via `PATCH /chat/sessions/{id}`) and the same question is re-asked, now scoped.
3. Either way, `backend/core/insurance_bot.py:ask_insurance_bot(query, chat_history, policy_id, policy_type, standalone_query, voice)` does retrieval + generation only (no LLM detection/rewrite calls of its own, so a turn costs at most one resolver-or-rewrite call plus one generation call):
   - **Retrieval** (`backend/rag/retriever.py:hybrid_search`, SQL in `backend/rag/chunk_store.py`): the vector store is the `chunks` table in Postgres (Neon) with pgvector. Dense search is `ORDER BY embedding <=> query` (cosine, HNSW index) over local `BAAI/bge-small-en-v1.5` embeddings run on ONNX via `fastembed` — no torch, no API quota; model cached under `.cache/fastembed` or `FASTEMBED_CACHE_PATH`. Sparse search is Postgres full text (`ts_rank_cd` over a generated `tsv` column, GIN index) with the question's words OR-ed together. The two run concurrently on separate sessions and are fused with weighted reciprocal rank fusion (0.5/0.5, k=60) in Python (no MMR). Then `retriever.py:rerank` calls the Jina Reranker API (`jina-reranker-v2-base-multilingual`, 3s timeout) — on any API failure it logs a warning and falls back to the fused order instead of failing the chat, reported as `rerank_fallback` in `timings`. `retrieve(query, policy_id, policy_type, user_id)` is the full pipeline. Scope: `user_id` (when given) always restricts to that user's chunks — chat paths always pass it, so one user can never retrieve another's; then `policy_id` (one specific policy) takes precedence over `policy_type` (`health`/`life`/`motor`, all of the user's policies of that type); neither means all of the user's chunks. Writes go through `chunk_store.replace_policy_chunks` in the caller's transaction, so there's no cache to invalidate.
   - **Context assembly**: retrieved docs are formatted into a text block carrying `policy_type`, `source_file`, and `page` metadata, and deduped into a `sources` list for citation.
   - **Generation** (`backend/chains/insurance_chain.py`): a Gemini chain (via `backend/core/llm.py:get_chat_model`, see "LLM calls and rate limits" below) answers using only the retrieved context, chat history, and a rules-based prompt (handles ambiguous multi-policy questions, waiting-period deductive reasoning, and unmatched medical terms). When `voice=True`, an extra `style_instruction` asks for 2-3 short spoken sentences with no markdown/tables, deferring long details to what's on screen.

Each stage of `ask_insurance_bot` is timed and returned in `result["timings"]`.

### Chat: ephemeral vs. persistent

Two distinct surfaces share `answer_question` but serve different purposes:

- **Floating assistant** (`frontend/src/components/FloatingAssistant.tsx`, mounted once in `App.tsx`'s shell so it's present on every page except `/chat`): a lightweight FAB → panel with Chat/Voice tabs. No persistence — `messages` is component state that resets whenever the in-scope policy changes (via `useMatch('/policies/:id')`). Calls the stateless `POST /chat`. Off a policy page it's unscoped, so a clarification can occur; picking a candidate chip sets a local `scopedPolicyId` that stays in effect for the rest of that floating conversation (until the policy context changes), so follow-ups aren't re-asked.
- **Chat page** (`frontend/src/pages/ChatPage.tsx`, route `/chat`): a two-pane ChatGPT-style UI — a session list (left) and the active conversation (right). Backed by `backend/models.py:ChatSession`/`ChatMessage` (new tables, no Alembic needed since `Base.metadata.create_all` creates new tables automatically) and `backend/routers/chat_sessions.py`: `POST/GET /chat/sessions`, `GET/DELETE /chat/sessions/{id}`, `PATCH /chat/sessions/{id}` (change/clear a session's `policy_id` scope), `POST /chat/sessions/{id}/messages`. Sessions are created lazily on first message (not eagerly on page load); a session's `title` is naively set from the first ~60 chars of the first user message (not LLM-summarized). Optional `?policy_id=` query param scopes a new session to a policy, matching the floating assistant's "Full chat →" link. A scope picker in the page header lets the user change (or clear, back to "All policies") a session's `policy_id` at any point, via that `PATCH` endpoint — this is the primary way to avoid ambiguous multi-policy retrieval, with resolver-driven clarification chips (rendered from `ChatMessage.meta.clarification_options`, via `ChatBubble`) as the fallback for unscoped sessions.

### Ingestion

Two paths write to the same `chunks` table.
All ingestion goes through `backend/rag/ingest_job.py` (`process(policy_id)` = parse + chunk + extract, `persist(policy_id, result)` = embed, then in one transaction replace that policy's chunks and update/mark the row `ready`/`failed` — a failure rolls back to the previous chunks). Only it and `backend/rag/ingest.py` import Docling (via `loader.py`), and Docling lives in the `ingest` dependency group, so the web process must never import `loader.py`. Each policy is processed in its own subprocess because converting more than one PDF in-process triggers a flaky native segfault in Docling's dependency stack (loky/joblib teardown race).
- CLI (`uv run python -m backend.rag.ingest --reindex-all`): re-runs `python -m backend.rag.ingest_job --policy-id N` (full job, in-process writes) for every `ready`/`failed` policy whose file still exists; `--only 3,5` limits it. Safe with the backend running (Postgres handles concurrent writers). This is also the command the planned Cloud Run Job will run.
- Upload flow (`backend/routers/policies.py:POST /policies/upload` → `backend/services/ingestion.py:run_ingestion_job`): the user does **not** pick a policy type — the row is created with `policy_type="unknown"` and the background job classifies it. It runs `ingest_job --policy-id N --out <tempfile>` (parse + extract only) in a subprocess, then calls `persist()` itself in the server process (a leftover from the Chroma days; Phase E of `DEPLOYMENT_PLAN.md` removes the `--out` handoff). `INGESTION_MODE` (`backend/config.py`, default `local`) is the switch for the planned Cloud Run Job mode. The job calls `extract_policy_summary(full_text)` itself and retroactively tags every chunk's metadata with the classified `policy_type` before returning (classification happens inside the same structured-output LLM call as the rest of the summary, not a separate round-trip). On success, `status="ready"` with `summary_json`, `chunk_count`, `insurer`, `product_name`, `policy_number`, `policy_type`, `sum_insured`/`sum_insured_numeric`, `policy_end_date`/`policy_end_date_iso` all promoted onto the `Policy` row; on any exception, `status="failed"` with `error_message`.
- `PATCH /policies/{id}` (body `{policy_type}`, one of `health`/`life`/`motor`) lets the user manually correct a wrong classification: updates the DB row and re-tags that policy's chunks in the same transaction (`chunk_store.set_policy_type`). Deleting a policy removes its chunks through the `chunks.policy_id` `ON DELETE CASCADE` foreign key. It does **not** re-run extraction — overriding health→life won't retroactively populate `life_details`; only a re-upload does.
- `GET /policies/{id}/file` returns the original uploaded PDF (`FileResponse`). It requires the bearer token, so the frontend never links to it directly: `frontend/src/api/client.ts:fetchPolicyFile` fetches it as a blob, used by `downloadPolicyFile` and by `PolicyViewerDialog` (an in-app modal showing the PDF in the browser's built-in viewer via an object-URL `<iframe>`, `#page=N` to jump to a page). The viewer is opened from anywhere via `AppShellContext`'s `openPolicyViewer(policyId, page?)`, including chat source chips (`SourceList` parses `"<file> (Page N)"` and matches `source_file` against the user's policies).

Both paths use `backend/rag/loader.py` (Docling `DocumentConverter` + `HybridChunker`, structure-aware — keeps tables intact, unlike a blind character splitter; `max_tokens=512`, counted with the same `bge-small` tokenizer the embedding model uses, which is also that model's input limit). OCR is conditional: `_needs_ocr()` checks the PDF's text layer with `pypdf`, and only if some page has under 50 chars of text does Docling run with full-page OCR — digital PDFs skip OCR entirely (it would only re-read logos). Each chunk carries `policy_id`, `policy_type` (null when not yet known), `source_file`, `page`, `section`, `chunk_index`, stored as columns of the `chunks` table (plus `user_id`, copied from the policy for retrieval isolation).

### Structured extraction

`backend/chains/policy_summary_chain.py`: `get_chat_model(schema=PolicySummary, max_wait_s=120)` (structured output; waits out busy minute windows since it runs in a background job, and retries only on `ModelOverloaded`), run once per upload against the full document text (Docling's markdown export, not retrieval chunks). `PolicySummary` includes:
- `policy_type: Literal["health","life","motor","unknown"]` — the LLM classifies from content (hospitalization/room rent/co-pay → health; sum assured/nominee/maturity → life; vehicle/IDV/registration → motor).
- One of `health_details` / `life_details` / `motor_details` populated (the other two `None`) with type-specific fields (e.g. health: room rent limit, pre/post-hospitalization days, co-pay %, network hospital info as free text; motor: IDV, NCB %, cashless garage network as free text — neither is a structured searchable directory, just what the document itself states).
- `faqs: list[FAQ]` — 4-6 policy-specific FAQs generated from the document.
- `sum_insured_numeric: float | None` and `policy_end_date_iso: str | None` — the LLM's own normalization (for dashboard aggregation/sorting); the raw string fields stay the source of truth for display.

### Voice I/O

Backend: `backend/voice/stt.py` transcribes with a local `faster-whisper` "base" model (CPU, `compute_type="int8"` for latency); `backend/voice/tts.py` synthesizes locally with Kokoro (`kokoro-onnx`, the 82M-parameter Kokoro model as int8 ONNX on CPU, one thread — no API, no quota; replaced Gemini TTS, whose free tier allows 10 requests/day, and then Piper, which sounded too robotic). Weights and voices are Apache 2.0; the voice is `af_heart` (`VOICE`). The model and voices files (~120MB) are downloaded on first use into `.cache/kokoro` (`KOKORO_MODEL_DIR`) and loaded at startup by `main.py`'s `lifespan` via `load_voice()`. `normalize_for_speech()` strips markdown and rewrites rupee amounts in Indian units (`₹5,00,000` → "5 lakh rupees"), since espeak (Kokoro's phonemizer) reads Indian digit grouping as "five zero zero thousand". Synthesis runs at ~0.6x real time on one core, so time to first audio is proportional to the first chunk's length: `split_for_speech()` makes one chunk per sentence, except that the first sentence's opening clause (≥3 words before a comma) is its own chunk; after that, synthesis stays ahead of playback. Extra ONNX threads barely help (2.7s → 2.1s per sentence on 4), and `_synth_lock` runs one synthesis at a time. `speak_stream(text)` yields one WAV per chunk; `POST /voice/speak-stream` sends each as a `[4-byte big-endian length][payload]` frame as soon as it's synthesized (first audio after ~2s), and `POST /voice/speak` returns the whole answer as one WAV. `POST /voice/transcribe` is unchanged (multipart → tempfile, cleaned up after).

Frontend: `frontend/src/hooks/useVoiceRecorder.ts` does real silence detection (Web Audio `AnalyserNode`, RMS over `getByteTimeDomainData`) instead of manual tap-to-stop — recording waits for the user to actually speak (ignores an initial silence window), then auto-stops 2.5s after they go quiet (long enough to pause and think mid-question; speech only counts once ~250ms of loud frames have accumulated, so a cough doesn't arm the timer), with a 30s hard cap. Both `FloatingAssistant` and `ChatPage` call this hook directly (rather than owning it inside `MicButton`) so they can drive it programmatically; `MicButton` is a controlled component (`recording`/`hasSpoken`/`onStart`/`onStop` props) plus a `speaking`/`onInterrupt` pair — tapping it while the assistant is talking stops playback and starts recording immediately (manual barge-in; there's no automatic voice-activity interruption during playback, since an always-on mic during TTS output risks picking up the speaker's own audio as false speech without guaranteed echo cancellation). `frontend/src/lib/audioQueue.ts:AudioQueuePlayer` consumes `speakTextStream` (`frontend/src/api/client.ts`, parses the length-prefixed frames) and plays each blob back-to-back via a single `<audio>` element, calling `onDone` once the queue drains; if `speakTextStream` fails before any audio arrived, both surfaces fall back to `AudioQueuePlayer.speakWithBrowser(text)` — the browser's built-in `speechSynthesis` voice — rather than answering in silence (`stop()` cancels it too, so barge-in still works); both surfaces use that to drive an opt-in "Hands-free" toggle that auto-restarts recording after the answer finishes playing, for a continuous voice-mode loop without a full realtime/speech-to-speech rearchitecture. `voice: true` is threaded through `ChatRequest`/`ChatSessionMessageCreate` for voice-originated turns, to get the shorter spoken-style answer from `ask_insurance_bot`. Both `FloatingAssistant` and `ChatPage` render the live transcript and the bot's text answer immediately (not just audio) — voice mode never jumps to a different tab/view.

### LLM calls and rate limits

All LLM chains (`backend/chains/*.py`) are LangChain LCEL pipelines (`prompt | llm | parser`) whose model comes from `backend/core/llm.py:get_chat_model(max_output_tokens, timeout, max_wait_s, schema=None)` — never construct `ChatGoogleGenerativeAI` directly. It rotates across `MODEL_ROTATION` (`gemini-3.1-flash-lite`, then `gemini-3.5-flash-lite`, each with its own quota) via `.with_fallbacks(..., exceptions_to_handle=(LLMUnavailable,))`, with the client's own `max_retries=0` (hidden retries would be untracked requests). Each model is wrapped in `RateLimitedModel`, which calls `backend/core/rate_limiter.py:acquire(model, estimated_tokens, max_wait_s)` before the request and `record_usage()` with the API's actual token count after; API 429/402 errors become `QuotaExceeded` and 503s, timeouts and dropped connections (`httpx.TransportError`) `ModelOverloaded` (both `LLMUnavailable`), which is what triggers rotation. Streams are read through `_iterate_with_stall_timeout`: if no chunk arrives within the model's `timeout`, the call is abandoned as `ModelOverloaded` — the HTTP read timeout alone didn't catch a generation stream that hung ~10 minutes until the server reset it. Chat-path chains use `max_wait_s=5`.

`rate_limiter.py` enforces RPM/TPM (sliding 60s window) and RPD (resets at midnight Pacific, like Gemini's) per resource from its `LIMITS` table — the AI Studio free-tier numbers for each Gemini chat model, plus `jina-reranker` (inferred ~100K TPM from observed 429s; confirm on the Jina dashboard) — at `SAFETY_FACTOR = 0.9`, since it can't see usage from outside this app. Counters live in SQLite (`backend/rate_limits.db`, `RATE_LIMIT_DB_PATH`) because calls come from both the server and ingestion subprocesses and daily counts must survive restarts; `BEGIN IMMEDIATE` serializes check-and-record across processes. A spent daily quota raises immediately; a full minute window waits up to `max_wait_s`, then raises. `uv run python -m backend.core.rate_limiter` prints current usage vs. limits. The Jina reranker calls `acquire(..., max_wait_s=0)` and falls back to fused order rather than wait. TTS is local (Kokoro) and isn't rate-limited. When every model is unavailable, `chat_service.answer_question_stream` turns it into a normal-looking answer ("I've reached my daily usage limit… try again in about N hours") with the usual `meta`/`token`/`done` events instead of breaking the stream. Updating limits (e.g. after enabling billing) is an edit to `LIMITS`.

### Backend

FastAPI + SQLAlchemy 2.0 + Postgres on Neon (`DATABASE_URL`; falls back to the local SQLite file `backend/policies.db` only for the non-vector parts, so a laptop without Neon can't run retrieval). The schema is managed by **Alembic** (`alembic/`, `alembic.ini`): the app does not create or alter tables at boot, so run `uv run alembic upgrade head` first. `alembic/env.py` reads `Base.metadata` and prefers `MIGRATION_DATABASE_URL` (Neon's direct, non-pooler URL) over `DATABASE_URL`; migrations that autogenerate can't express (like `CREATE EXTENSION vector`) are edited in by hand. The engine uses `pool_pre_ping` and `pool_recycle=300` because Neon suspends idle compute. `backend/db.py:get_db()` is the request-scoped session dependency; `run_ingestion_job` opens its own `SessionLocal()` since it runs on Starlette's threadpool, not the request thread.

Routers: `auth` (`POST /auth/signup`, `POST /auth/login`, `GET/PATCH /auth/me`, `POST /auth/change-password`), `policies` (list/get/upload/delete/patch-type/download-file), `chat` (`POST /chat`, ephemeral), `chat_sessions` (`/chat/sessions*`, persistent, including `PATCH /chat/sessions/{id}` to change scope), `voice` (`POST /voice/transcribe`, `POST /voice/speak`, `POST /voice/speak-stream`). The `core`/`chains`/`rag`/`voice`/`services` submodules under `backend/` hold all the RAG/LLM/voice/orchestration logic.

### Authentication

Real signup/login/logout, backed by a `User` table (`backend/models.py`) and stateless JWT bearer tokens — no cookies, no server-side session/blacklist. `backend/security.py` hashes passwords with `bcrypt` directly (not passlib — `passlib`'s `CryptContext` bcrypt backend probes `bcrypt.__about__.__version__`, which recent `bcrypt` releases removed, breaking on first hash/verify call) and signs/verifies JWTs (`python-jose`, `HS256`, `SECRET_KEY`/`ACCESS_TOKEN_EXPIRE_MINUTES` from `backend/config.py`, default 7-day expiry). `backend/deps.py:get_current_user` is a FastAPI dependency (via `HTTPBearer`, not `OAuth2PasswordBearer`, since every endpoint here takes JSON bodies) added to every `policies`/`chat`/`chat_sessions` route — data is scoped per user via a nullable `user_id` FK on `Policy` and `ChatSession` (nullable because it was added to existing tables after the fact, which can't retroactively add `NOT NULL` constraints; ownership is enforced in the routers instead, treating a mismatched `user_id` the same as not-found — 404, not 403). `ChatMessage` has no `user_id` of its own, scoped transitively via its parent session. `backend/services/chat_service.py`'s unscoped-chat policy resolution (`_list_ready_policies`) also filters by `user_id` so a user's unscoped chat can't resolve against another user's policies. The frontend (`frontend/src/context/AuthContext.tsx`) stores the token in `localStorage` and `frontend/src/api/client.ts` attaches it as `Authorization: Bearer <token>` on every request, redirecting to `/login` on any `401` via a module-level callback set by `AuthContext`. `frontend/src/components/RequireAuth.tsx` gates the entire authenticated route tree in `router.tsx`.

`Policy` columns beyond the obvious: `policy_number`, `sum_insured` (str) + `sum_insured_numeric` (float), `policy_end_date` (str) + `policy_end_date_iso` (str) — all nullable.

### Frontend

Vite + React 19 + TypeScript + React Router 7 + Tailwind v4 (via `@tailwindcss/vite`, no `tailwind.config.js` — palette tokens live as `@theme` custom properties in `frontend/src/index.css`: `sage`, `teal`, `cream`, `peach`, `beige`). **Light theme only, by design** — there is no dark mode; `color-scheme: light` is set explicitly and no component uses `dark:` variants, since the calm sage/cream palette from `UIUX.md` is the one intended look, not something to auto-invert.

`frontend/src/App.tsx` is the authenticated shell: `Sidebar` (Home/My Policies/Upload Policy/Chat/Reminders/Profile) + `Topbar` (search input is visual-only, no backend search endpoint) + `<Outlet/>` + `FloatingAssistant`, all inside a `h-screen overflow-hidden` layout where only the `<main>` content area scrolls (sidebar/topbar stay pinned). `frontend/src/context/AppShellContext.tsx` shares upload-dialog open/close state and a `policiesVersion` refresh counter across pages without prop drilling.

Routes (`frontend/src/router.tsx`): `/login` and `/signup` (outside the shell, real auth against the backend — see Authentication above) and, inside the shell (wrapped in `RequireAuth`, redirecting to `/login` when unauthenticated): `/` (`HomePage` dashboard: stat cards + recent policies), `/policies` (`PolicyListPage`: type filter chips, `PolicyCard` grid, drag-and-drop upload with progress via `XMLHttpRequest`), `/policies/:id` (`PolicyDetailPage`: header + `PolicyDetailTabs` — Overview/What's Covered/Claim Process/Cashless Hospitals/FAQs — plus a manual policy-type override control), `/chat` (`ChatPage`, see above), `/reminders` (`RemindersPage`: ready policies sorted by `policy_end_date_iso`), `/profile` (`ProfilePage`: editable name/email/phone, change password, logout — real account settings backed by `/auth/me`).

`src/api/client.ts` is a thin wrapper: `fetch` for JSON endpoints, `XMLHttpRequest` for `uploadPolicy` specifically (needed for `xhr.upload.onprogress` — `fetch` can't report upload progress). No state library — local `useState`/`useEffect` plus a small `usePolling` hook (`PolicyDetailPage` polls every 2s while `status === "processing"`).

## Known issues to be aware of

- `vectordb/` (the old Chroma data) is unused and safe to delete; Chroma, `rank-bm25` and `langchain-chroma` were removed from the dependencies.
- Changing the embedding model or dimensions means a new Alembic migration for `chunks.embedding` (`models.py:EMBEDDING_DIM`) plus `--reindex-all` — never mix different models' vectors in one table.
- `backend/rate_limits.db` is per-machine: with several Cloud Run instances each would count separately, so the `api_calls` table has to move to Postgres (Phase C of `DEPLOYMENT_PLAN.md`).
- The Jina free-tier key rate-limits bursts (429s after a few dozen reranks in a minute); `rerank()` falls back to fused order when that happens. Fine for interactive chat, but run evals with `--delay` and expect fallbacks under concurrent load until the key is on a paid tier.
- A backend process restart mid-ingestion-job leaves the `Policy` row stuck at `status="processing"` forever (no retry queue) — recovery is deleting and re-uploading.
- `PATCH /policies/{id}` fixes the type label and retrieval filtering but never re-runs extraction, so a corrected type won't retroactively gain that type's `*_details` — only a fresh upload populates those.
- "Cashless Hospitals"/garage network info is whatever free text the policy document itself states — there's no directory, search, or maps/geolocation integration, by design.
- Chat session titles are a naive first-message truncation, not LLM-generated summaries.
- Policies and chat sessions created before authentication was added have `user_id = NULL` and are permanently inaccessible through the API now that every query filters by the logged-in user — there's no reassignment/claiming flow; recovery is re-uploading the policy as the correct user.
